# 旧数据根目录保全与快照兼容设计

日期：2026-10-11（北京时间）

状态：用户已选择方案 1，并明确回复“同意，开始开发和测试”，本设计已批准实施。旧数据所属工作区和真人负责人用户名未提供；迁移和生产交付仍受此阻断。

## 目标与边界

保全旧数据根目录中的已知数据、未分类文件及空目录，避免把未分类目录当缓存丢弃。新增能力沿用现有离线快照、验证和独立恢复链路，不另建迁移系统，不给未知文件分配工作区，也不把它们加载到 Agent 上下文或工具目录。

本设计不授权生产切换、停止现有 LACK、修改 Tailscale Peer Relay、占用 443、安装全局软件、读取聊天中的凭据或改写原始数据。完整归档校验不是应用恢复、真实模型调用或 Muse 老镇/dots 玄玑接入验收。

## 已有证据与缺口

2026-10-11 的只读核对发现 12 个未分类根目录：`.github`、`agent_memories`、`build-cache`、`git`、`home`、`jspace`、`k8s`、`lack_repos`、`lineage`、`logs`、`thread_repos`、`workspace`。其中 8 个有直接子条目，4 个为空；没有据此确认子条目类型、内容或用途。

此前独立恢复试验校验了 28 项记录，但没有覆盖这些目录。SQLite 中 `agent_memory` 的行数不能代表文件系统记忆是否为空。此前的 `migrationReady=false`、`restoreReady=false` 和 `applicationConsistency=not_proven` 继续有效。

本设计依据：`docs/verification/2026-10-11-legacy-root-preservation-gap.md`。历史证据不是当前生产状态的重新检查。

## 方案选择

采用版本化快照 v2。不在 v1 中悄悄加入旧验证器可能忽略的空目录，也不把所有旧文件直接放进可执行候选目录。

新工具继续验证和恢复合法 v1 快照，但明确报告旧格式的范围限制。v1 的成功验证不能升级为完整根目录保全。旧工具遇到 v2 必须拒绝版本，不可忽略新字段后继续迁移。

## 数据布局与覆盖规则

```text
snapshot/
  snapshot-state.json
  manifest.json
  archive/
    config/lack.config.json          原配置的私有副本
    legacy-root/...                 未分类内容，只归档，不启用
  candidate/
    config/lack.config.json          保持未就绪的候选配置
    db/...                          已知 SQLite 的独立规范化副本
    memory|research|uploads|artifacts|attachments/...
```

归档范围不只枚举目前发现的 12 个名字。先有界遍历整个源根目录，识别每个目录和文件，再用确定的规则分类；未来出现的新普通条目也不能被静默遗漏。

| 源条目 | 处理方式 |
| --- | --- |
| 已知配置 | 原件私有归档；候选配置按现有规则生成，仍未就绪 |
| 已知 SQLite 主库及其支持文件 | 沿用稳定副本读取和规范化数据库备份；单独记录支持文件处理策略 |
| 五个已知文件目录及其空子目录 | 保全到候选文件目录，不改变既有内容授权边界 |
| 未分类根目录、文件，以及 config/db 中非已知条目 | 保全到 archive/legacy-root，保留源相对路径，保持未归属 |
| 符号链接、目录联接、设备、套接字、管道等非普通条目 | 拒绝本次准备，给出不含内容的阻断原因，不跟随、不跳过 |

已知数据库备份是逻辑规范化副本，不承诺与原始 SQLite 主库/WAL 逐字节相同。主库、WAL、回滚日志等源状态必须被明确识别和记录；不复制正在变化的支持文件后伪称可恢复数据库。非空回滚日志仍阻断。未知数据库仅作为稳定普通文件归档，不承诺其应用一致性，也不自动打开。

## v2 清单与兼容接口

快照状态和清单明确使用版本 2；独立恢复试验的标记版本也明确区分 v1/v2。现有导出函数保留，不借机改变调用方式或增加生产迁移入口。

v2 清单保留现有快照 ID、摘要、未解决项及未就绪标记，并增加以下可验证语义：

- 文件记录：目标相对路径、类型、源相对路径、大小和 SHA-256；生成的候选文件明确标记为派生记录。
- 目录记录：目标相对路径及对应源目录，包含空目录；目录不能靠 mkdir 的副作用隐式表示。
- 源覆盖清单：每个源条目必须恰好对应一种处理策略；数据库支持文件不能冒充普通目标文件，也不能无理由消失。
- 范围结果：完整有界根目录清点、已知数据库逻辑保全、未分类数据仍未归属；不得使用单个成功布尔值掩盖差异。
- 一致性结果：源稳定性检查的范围和结果；应用一致性仍为 `not_proven`。

验证器按版本分支。v1 保持旧校验规则并报告部分范围；v2 校验目录、文件、源覆盖关系及派生记录。拒绝重复路径、文件/目录冲突、未知类型、越界路径、未列出的文件或目录、缺失空目录、大小或摘要不符，以及不合法的覆盖关系。

源覆盖清单不能凭自身证明真实源没有遗漏。准备阶段必须对实际源遍历做前后比对；验证报告必须说明当前验证是源对照校验，还是仅对离线包的内部完整性校验。

## 安全与资源限制

- 保持既有上限：单文件 64 MiB、总文件体积 512 MiB、最大深度 12；条目上限 4096 同时计入文件和目录，不自动放宽。
- 清单读取继续有界，超过 2 MiB 拒绝；达到任一上限先报告阻断，不自动追加容量或删除旧文件。
- 拒绝绝对路径、反斜杠歧义、控制字符、空段、`.`、`..`、盘符及链接父路径；源和目标不得重叠。
- Linux 私有目录 0700、文件 0600，所有者及链接检查保持有效；源执行权限只作为元数据，不自动恢复可执行权限。
- Windows 验证不冒充已证明 POSIX 权限；Linux 原生试验单独验收实际权限。
- 原配置及未知文件可能含凭据，只保留在服务器私有归档；不得打印内容、下载到公开材料、提交 Git 或自动载入运行时。
- 摘要用于完整性检查，不等同身份认证。验收时在独立受控报告中保留清单摘要，不能只信任同一可修改包中的摘要。

准备前后比较源条目集合、类型及文件身份/大小/摘要；新增、删除、改名、文件变化或空目录变化都必须使本次准备失败。失败只清理由本次操作创建且已确认归属的临时资源，不改原目录，不停止写入者，也不把部分结果标成准备完成。

在线稳定性比对不等于所有应用数据的事务一致快照。日志频繁变化或内容超限时，下一步是报告原因并单独确认一致性获取方案，不能无限重试、自动停止生产或降低安全检查。

## 独立恢复与消费方

独立恢复从已验证清单重建所有文件和目录，再验证目标包。必须保留空目录，不能只遍历文件记录；在复制结束后重新验证源快照，阻止中途变化。

新恢复工具支持旧 v1 包，但输出其历史范围限制；新 v2 包的目录覆盖不能在恢复时丢失。未知格式拒绝。恢复试验仍是隔离目标，不替换现有数据，不创建工作区归属，不生成可运行就绪状态。

所有读取快照或恢复结果的迁移、恢复和启动前置检查消费方需核对版本及能力。消费者只能使用明确支持的格式；不能把归档中未分类条目复制进运行目录，也不能因新增归档成功消除 `explicit_ownership_required` 或 `owner_identity_requires_bootstrap`。

## 实施与验收顺序

1. 用户审核本设计；之后提交具体实施计划。旧数据工作区及负责人单独确认，不猜测。
2. 建立失败回归：文件系统记忆、仓库成果、未知 config/db 条目及空目录此前未完整保全；保留 v1 固定样本以证明兼容读取。
3. 一次小范围实现 v2 清点、验证、恢复和必要消费方保护，不启用生产迁移。
4. 定向测试覆盖源变化、缺失/新增/重复目录、路径穿越、链接、格式版本、摘要、权限和资源上限；归档成功仍不得允许启动未归属数据。
5. 运行完整本地回归及 HTTP/WebSocket/SQLite smoke；失败必须修正后复测，不用旧的 477 项结果代替新版本验收。
6. 在既有授权的 VPS 隔离范围内预检并复验：独立私有目录、回环或无网络、明确 CPU/内存/任务数/超时上限，不全局安装、不占 443、不停 LACK/Relay。
7. 原生核验源范围、目录结构、文件摘要、数据库完整性与权限；对照生产 PID、重启次数和健康状态，清点自有试验资源。该检查不冒充 Relay 实际转发吞吐测试。
8. 同步审计提交到 cloud-agent-pilot-foundation，报告通过、失败和待验证项；应用恢复、生产切换、真实模型及外部 Agent 接入仍另行完成。
