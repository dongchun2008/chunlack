# ChunLACK 多用户、多工作区公网访问与 Agent 接入设计

日期：2026-10-09。状态：待用户审阅的设计，不是已部署记录。

## 目标与授权范围

用户选择公网 HTTPS 接入、提供域名 chunclaw.top，并同意分别使用 lack.chunclaw.top 作为网页入口、agents.chunclaw.top 作为 Agent 接口。用户进一步明确必须考虑多个真人用户登录同一或不同工作区。要求保护既有服务并尽量减少硬件消耗。新增公开范围为经过独立真人账号认证及工作区授权的 LACK 页面和必要 HTTP/WebSocket 路径，以及经过节点鉴权和工作区授权的受限 REST/MCP 接口。底层服务继续仅监听 loopback；网关管理、配对、模型接口、任意文件访问与任意命令执行不得成为公开的无约束接口。保留 Ollama 和供应商中立模型路由。

本设计替代上一版的单所有者网页假设。真人账号、工作区成员关系、角色、会话和业务数据隔离属于公开网页交付的必要范围，不留到公网开放之后补做。网页中的既有操作仍须逐项映射和测试，不能因为套上登录就宣称所有执行边界已完善。外部 Agent 不得通过节点凭据进入真人网页。完整通用 Tool Gateway 不作为已实现能力；未完成边界验证的工具操作继续禁用。

公网接入是对上一阶段“不开放公网端口”的明确范围变更，不意味着允许改变任何现有服务。真实账号凭据录入、绑定和安全授权仍采用供应商支持方式，不将密钥放入聊天、源码、日志或本设计。

## 部署选项与选择

推荐一套轻量应用支持多个工作区：Caddy 承载两个 HTTPS 虚拟站点，应用承担真人会话、成员授权和工作区业务隔离，节点网关复用现有 store/artifacts/MCP/SDK 模块并补充工作区上下文。优先复用现有 Node/SQLite 基础，不另建任务协议，不引入 Redis、Docker、消息代理、模型或浏览器服务。SQLite 的工作区隔离由受约束的数据访问层和覆盖测试落实，不宣称具有数据库原生行级安全。

替代方案一是接独立 OIDC 身份系统：适合已有统一身份服务时复用，但只能解决身份认证，仍须改造 LACK 的工作区授权，初期不另部署大型身份服务。替代方案二是每个工作区启动一套 LACK：可提供更强的进程隔离，但增加内存、升级和备份负担，不作为当前小规格 VPS 的默认方案。推荐方案是本次书面设计建议，待用户审阅后进入实施计划。

多用户隔离不能仅靠旁路代理或隐藏前端菜单实现，必须改造 LACK 的 HTTP、WebSocket、业务上下文和持久化路径。先在本地候选版本及独立测试数据中开发，现有生产 LACK 和 Relay 保持不变。上线时优先采用独立目录和状态的候选实例，是否能与旧实例短期并存由资源实测决定；若需要更新或切换现有 LACK，另行批准维护窗口，不以“旁路部署”掩盖重启或数据迁移。

应用与网关是否合并进程在实施计划中根据故障边界和资源测量决定，不为每个用户或工作区增加常驻进程。进程合并不能代替工作区授权，也不能在未批准的情况下更新现有生产进程。

若现场已有合适反向代理，优先审查后复用独立站点；若没有，采用官方标准 Caddy 独立实例。不替换系统已有代理、不接管占用中的 443。已有代理的 reload 也不能当作无风险默认动作，需单独确认。

## 域名、证书与连接

域名用途已获用户同意：lack.chunclaw.top 用于真人网页，agents.chunclaw.top 用于节点 REST/MCP。不同工作区通过站内工作区选择器切换，不需要各建一个域名或部署实例。二者都是 ChunLACK 的入口，不是两套系统。实施前仍须在用户的权威 DNS 管理中确认两条记录是否已有用途；不能覆盖未知用途的记录。此前公开 DNS 对 lack.chunclaw.top 的 A 查询返回 NXDOMAIN，HTTPS 探测超时；这不是本次重新检查，不证明该名称在 DNS 管理中无人使用，也不证明服务已经部署。不得改 chunclaw.top、books.chunclaw.top 或其他既有记录。经确认后，两条新记录目标是上述 VPS 公网地址；IPv6 未验证时不新增 AAAA。

网页路径：真人浏览器 -> lack.chunclaw.top TCP 443 / 可信 HTTPS -> 应用账号会话 -> 工作区成员及操作授权 -> 已完成隔离改造的 loopback LACK HTTP/WebSocket 服务。不得将未改造的现有 LACK 直接代理为多人网页。

节点路径：Muse REST 或 dots MCP -> agents.chunclaw.top TCP 443 / 可信 HTTPS -> loopback 节点入口 -> 节点身份及工作区授权 -> 同一个网关 store 与附件模块。初期运维管理入口保持 loopback，网页的工作区成员与资源管理只开放明确受角色控制的业务接口。两个域名不得默认回落到同一个后端，也不得通过修改 Host 获得另一个入口的权限。

证书采用标准自动续期；优先评估仅 TCP 443 的 TLS-ALPN-01，禁用 HTTP challenge、自动 HTTP 跳转及 HTTP/3，避免隐式新增 TCP 80 或 UDP 443。DNS、443 占用、CAA 或中间代理使该方案不可用时停止并报告，不自动改用开放 80、通配证书、DNS 凭据或跳过 TLS 校验。

内部 HTTP 仅限 127.0.0.1 的明确新增模式；既有默认 HTTPS 门面的校验保持不变。公网不信任调用者的 Host、Forwarded、X-Forwarded-* 身份声明，不能让反向代理扩大路径或主体验证范围。

## 真人账号、登录与会话

不采用共享密码或 Caddy Basic Auth 作为多人系统的身份来源。每人一个平台级账号，可加入多个工作区；不因工作区变化重新注册账号。初期采用邀请制，不开放任意注册，不依赖公共邮件服务。受授权的工作区所有者可创建有时限、一次性且绑定目标工作区及角色的邀请；新用户设置个人密码，已有用户先登录再接受。邀请及重置凭据仅保存摘要，不写入访问日志或 Git，不用已存在邮箱的声明自动合并身份。

使用受维护的认证组件或标准密码哈希实现，不自行设计密码加密算法。哈希参数、登录前限流和并发上限须在小规格环境中测量，不能用降低安全性换取表面速度。账号和节点凭据、SSH 密码、模型密钥相互分离。工作区所有者不能读取或设置成员的现有密码，密码恢复使用有时限的一次性流程并撤销旧会话。

建议服务端可撤销的不透明会话，浏览器只持有 Secure、HttpOnly、SameSite=Lax 的 host-only Cookie，不设置覆盖 chunclaw.top 的 Domain，不把会话令牌放入 localStorage 或 URL。会话标识只存摘要；登录后轮换标识，初始建议空闲 30 分钟、绝对 12 小时到期，支持主动退出、退出全部设备和账号停用。权限以当前成员关系为准，不把所有工作区权限固化在长期令牌中。agents.chunclaw.top 不接受真人 Cookie 或网页密码。

登录页面及必要无敏感内容的静态资源可匿名读取，业务页面和资源必须认证。工作区内的业务请求还必须通过成员及操作授权。改变状态的 HTTP 请求采用 CSRF 令牌与精确 Origin 校验；WebSocket 握手验证会话、精确 Origin 和工作区成员身份，拒绝跨站、null 和缺失 Origin。正常无 Origin 的导航限于已确认无副作用的读取路径，不假定所有 GET 都安全，不使用宽泛 CORS 或 Referer 代替认证。既有前端的同域 WebSocket 建连方式保留，但连接和每条业务消息都须授权。

注销、会话到期、账号停用或成员移除后，立即撤销对应访问并关闭相关 WebSocket，不能只限制下一次握手。切换工作区时退出旧订阅、清空前端工作区状态并建立新授权上下文；每个标签页和每条请求独立携带选择信息，禁止进程级或会话级可变“当前工作区”造成并发串流。服务端把客户端工作区 ID 当选择器，而不是权限凭证。

网页代理只开放已梳理的必要路径，限制请求体、超时和连接数。保持现有视觉风格，新增登录、工作区切换和最小成员管理界面，不做无关视觉重构。对登录、邀请、密码重置和节点入口分别设置有界防护，且密码哈希前完成流量准入；缓存容量与过期必须有上限。记录安全事件但不记录密码、Cookie、授权头或敏感正文。

## 工作区与权限模型

结构为：平台账号 -> 工作区成员关系 -> 工作区内的项目、频道和任务。多个真人可同时在同一工作区协作；同一真人可在不同工作区拥有不同角色。初期项目和频道继承工作区权限，不承诺尚未实现的私密频道、私有项目或跨工作区共享。个人资料和个人记忆另加用户范围，不自动成为工作区共享资料。

建议最小角色：所有者负责成员、工作区配置、节点授权、配额和高风险审批；成员可参与讨论、创建及执行被许可的任务，但不能管理成员、获取密钥或扩大节点权限；只读成员仅查看被许可内容，不能发起任务、触发模型费用、审批或上传修改。所有者不能移除或降级最后一名有效所有者；角色变更须事务化并审计。检索员、核验员、汇总员仍是任务分工，不对应这些真人权限。

平台维护权限与工作区权限分开。初期工作区创建和账号停用由受控运维入口处理，普通用户不自动获得创建任意工作区的权限；平台维护人员没有通过普通业务接口默认浏览所有工作区内容的权限。此处是应用逻辑隔离，不承诺抵御可读取服务器文件和数据库的 root 管理员。

每个节点凭据初期只绑定一个工作区，并绑定能力及任务范围。物理设备可被多个工作区显式授权，但分别配置逻辑节点身份、凭据和任务执行范围；不能因为同属一台设备而共享文件、结果或凭据。模型服务可以被多个工作区授权共用，只共享推理容量，模型调用输入、输出、缓存、记忆与账务按工作区隔离。任何成员都不能直接获得底层模型密钥。

默认不跨工作区委派任务、查询记忆或共享附件。工作区内的自动委派仍受节点能力、审批、次数、预算和停止条件限制。未来跨工作区共享需单独设计授权和审计，不依赖 Agent 在提示词中自称有权限。

## 数据、消息及执行隔离

认证入口生成并向下传递不可被客户端覆盖的用户或节点身份及已验证 workspace_id。任务、计划、委派、消息、Moderator 状态、Memory、研究来源、附件、订阅、回调事件、审计和费用记录均须明确工作区归属；用户私有数据同时校验 user_id。共享的模型或节点目录只暴露当前工作区获授权的条目，不展示其他工作区名称和资源。

数据访问层强制按 workspace_id 查询、写入和关联，缺失上下文拒绝执行，不回落到默认工作区。关联约束和唯一键阻止任务或附件连接到其他工作区。原始 SQL、导出、搜索、后台 sweep、重试、事件回调、缓存和备份都纳入清单，不能只给 HTTP 列表加过滤。跨区资源请求不泄露其存在与内容。WebSocket 广播按经授权的工作区及频道路由，不向所有连接广播后让前端过滤。

附件使用工作区分区及规范化路径，下载和上传均校验归属；阻止路径穿越、符号链接越界和共享路径猜测。节点任务包括服务器绑定的工作区、任务 ID 与审批范围，回传校验原任务归属，事件签名和去重键包括相应范围。云端模型或外部 Agent 收到内容属于显式授权的数据外发，不把私有部署等同于资料永不离开服务器。

shell、文件及 Git 访问必须绑定授权工作目录和能力，不允许普通成员借共享节点执行任意命令；项目仓库访问使用单独授权的路径及凭据。跨用户或跨工作区共用高权限执行环境的隔离风险未解决前，相关能力不得作为多人系统公开交付。公开资料浏览试点不自动解锁这些工具。

旧数据不能批量标为所有用户可见。迁移前完成备份和恢复试验，由用户指定旧数据归属的初始工作区及所有者；无法确认归属的记录隔离并报告。先在副本迁移，保留版本及迁移清单，失败不启动公网多人入口。不自动修改生产数据库，也不同时运行两个写入同一状态目录的实例。

## 多人资源边界及验收试点

真人登录数、工作区数、在线 WebSocket 数和模型/Agent 执行并发是不同指标。多个真人在线不意味着每个人启动独立服务；不同工作区共享全局执行容量，再按工作区排队、限额和公平调度，防止一个工作区耗尽全部资源。节点和工作区权限变化后，排队任务重新检查授权，不继续使用已撤销凭据。

第一轮建议 3 个测试账号、2 个工作区：甲仅为 A 所有者，乙为 A 成员和 B 所有者，丙仅为 B 只读成员。验证甲乙同区协作、乙跨区切换及角色差异、丙不能触发任务或模型费用、甲不能进入 B、丙不能进入 A。同时测试乙的两个标签页分别留在 A/B 不串流，并测试成员移除后已有连接失效。

沿用保守试点的全局单执行槽和最多 5 个已注册节点，而不是每个工作区各放行 5 个并发任务。逐步测量登录、空闲连接、模型等待、附件处理及失败登录下的内存、CPU、延迟和 Relay 对照。既有资源上限只是初始预算，不是多人容量保证；无法在预算内运行时报告瓶颈，由用户决定调整容量或上线范围，不自动降低安全要求或扩大限制。

## 网关与任务边界

单个独立网关 runtime 是该公开节点队列的唯一所有者；REST、MCP、附件与事件使用同一 store 对象，保留现有租约、取消、撤销和结果证据校验。不得让两个实例直接双写旧网关数据库，不复制旧凭据或旧数据库形成另一份“主队列”。现场发现已有启用的 Agent Gateway 时，暂停启动，先决定受控对接，避免重复派单。

第一项真实接入验收维持 browser.public_read / public / 固定 example.com、最多五个登记节点、一个执行槽、90 秒租约、五分钟截止。现有 research.verify / research.summarize 和一般任务不因为公网开放而自动授予第三方；通用能力按后续明确能力与权限配置扩展。

旁路接口就绪不等于原 LACK 页面已能完整编排新节点。交付必须分别记录：公网入口通过、老镇真实执行通过、玄玑真实执行通过、LACK 任务发起与结果呈现通过。最后一项若需更新原 LACK，只能另行批准维护窗口；未完成时明确标为整个平台尚未交付，不用手工试点冒充自动协作。

agents.chunclaw.top 只允许现有明确白名单的节点 REST 路径、OpenAPI 和 POST /mcp；网关运维管理、配对、任意代理、任意文件下载、shell 与 Git 操作一律不公开。授权任务的截图附件仍经既有受限上传、工作区归属校验及内容验证流程处理，不等于开放文件系统。控制 JSON 256 KiB、截图 2 MiB、附件试点全局总量 20 MiB/七天，并另行限制工作区占用，保持内容验证。部署运行入口负责有界 sweep、附件清理、事件投递和正常关闭，不依赖测试脚本常驻。网页入口采用独立真人会话与工作区授权，不借用节点白名单作为网页鉴权。

公网新增鉴权前的有界并发/流量防护，不能只依赖登录后每节点限速。来源缓存有容量与过期上限；不以第三方 Caddy 限流插件增加维护负担。设置超时、连接数和 body 上限；日志不记录授权头、正文、回调签名或查询凭据。默认拒绝查询参数凭据和异常路径。

## 资源与现有服务保护

不运行 GPU 推理、云端浏览器、本机模型、Redis、Docker 或数据库服务。SQLite、内置 Node 模块、独立低权限用户及 systemd 限额足够用于首轮串行试点。

初始建议而非实测承诺：新 Node 服务 MemoryMax 192 MiB、CPUQuota 20%、TasksMax 32；新 HTTPS 服务 MemoryMax 128 MiB、CPUQuota 10%、TasksMax 64。限额不是预留或实际消耗，也不保证在该限额下稳定。验收失败时停止新增服务，不自动扩容或调整原服务限额。

部署前获取现有服务状态、PID/NRestarts、Relay UDP 端口及配置摘要、TCP 监听、可用 RAM/磁盘、swap、PSI、近期 OOM、真实 Relay 连通性及可重复延迟基线。只读获取必要字段，不导出 Tailscale 状态文件或凭据。

不运行 tailscale up/down/set，不重启 tailscaled，不改 DNS 路由、exit-node、转发、Relay 端口、已有防火墙规则或现有 systemd 单元。新增公网安全组/防火墙许可仅限已确认的新 TCP 443 入口，不清空、重载或重建现有规则集合。操作范围逐项记录。

真实 Relay 对照从参与的现有节点测量，不只调用 health。先运行低并发公开试点；出现新 OOM、持续内存压力、Relay 重启/掉线/丢包或明显延迟退化时停止新增流量并回滚新增入口。零影响不能仅凭资源上限或端口不冲突承诺。

## 接入与验收顺序

1. 确认本设计、独立子域名以及受信任远程操作方式，形成逐文件实施计划；未满足前不部署。
2. 本地测试入口路由、鉴权前限额、请求异常、TLS、租约、幂等、取消、事件与附件生命周期。完整测试和冒烟必须通过。
3. 现场只读刷新基线、备份必要配置与数据；备份不停止原服务，运行中的 SQLite 用一致性备份方式，不直接拷贝未处理的 WAL 数据集。
4. 在新目录部署审阅版本，复用已有专用 Node 运行时但不覆盖；依赖预制或有界安装，不触发 OS 升级或重型构建。先仅 loopback 启动并验收。
5. 核对独立 DNS、可信证书及拟开放端口，按批准范围开启新 HTTPS 入口。外部测试失败不得用关闭证书校验、开放管理端口或改 Relay 来解决。
6. 老镇用官方自定义连接器和安全凭据存储走公网 REST；验证真实浏览器活动、截图与结果，不能复用 Gadgets token 或模拟执行。
7. 玄玑走公网 MCP 和 MCP Events，不使用 OpenAI Tunnel；回调主机以真实账号返回值核对并显式允许，不猜测域名或使用通配规则。验证一次真实事件、浏览器和结果闭环；2xx 只表示通知收件。
8. 真实节点上线需用户完成供应商的具体安全授权；不替用户批准新安全敏感访问。最后完成 LACK 编排与结果呈现验收，形成已完成/未完成清单、使用说明和独立回滚记录。
